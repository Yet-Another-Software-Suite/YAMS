Detailed Description

Configuration for an active disturbance rejection controller.

Written by FRC Team 8331, who contributed active disturbance rejection control to YAMS.

An active disturbance rejection controller lumps everything the mechanism model does not capture (friction, back-EMF, game-piece loads, dropped battery voltage, unmodeled dynamics) into a single "total disturbance" and estimates it live with an extended state observer. The estimate is cancelled out of the control law, so the closed loop behaves like a clean chain of integrators that settles in the time you ask for. There is no proportional, integral or derivative gain to tune: you describe the plant (order and input gain) and the response you want (settling time), and the controller derives its own gains.

This is the drop-in equivalent of a PID: pass it to SmartMotorControllerConfig::WithADRCController and the motor controller runs the controller on its closed loop thread.

config.WithADRCController(yams::math::ADRCConfig{}
.WithSystemOrder(yams::math::ADRCConfig::SystemOrder::FIRST)
.WithSettlingTime(200_ms));

The output limit and ramp come from the motor config, as for every closed loop controller: WithClosedLoopMaxVoltage limits the output, and WithClosedLoopRampRate limits how quickly it changes.

Every value starts empty. The getters return that empty optional, and the controller fills it with the default documented on the With method. The system order has no default: BuildController throws until it is set.

The With methods only accept values the controller can use: anything else throws std::invalid_argument and leaves the config as it was. The controller reads its settings from this config every step instead of keeping copies, so the config never holds a value it cannot run.

Once a controller is built from it, the config also holds what the controller needs that the settings do not give: the control period, the b0 used while it is unset, and the gains worked out from them. The config works the gains out again whenever its settling time, bandwidth scale or b0 changes, so every live-tunable value takes effect on the controller's next step. The system order, input delay and tracking differentiator only take effect when a controller is built, and a built config refuses a different system order.

Copies are deep: a copy has its own settings, built values and gains, and raises its own alerts. Every method is safe to call while the controller's thread runs.

enum class yams::math::ADRCConfig::SystemOrder
strong

Plant order: how many integrators sit between the motor voltage and the measured output. Velocity loops on a DC motor are FIRST. For a position loop, POSITION and its aliases choose between first and second order when the controller is built, from the motor, gearing and inertia.

Enumerator
FIRST 

First order: the loop commands and measures velocity, such as a flywheel.

FLYWHEEL 

A flywheel's velocity loop; the same as FIRST.

SECOND 

Second order: a position loop whose inertia sets how fast it moves. POSITION chooses for you.

THIRD 

Third order: the measurement sits two integrations behind the voltage. Rare.

FOURTH 

Fourth order: three integrations between the voltage and the measurement. Rare.

POSITION 

A position loop whose form is chosen when the controller is built from a motor config, from the motor's back-EMF time constant at the mechanism, J * R / (G^2 * Kt * Ke). Under kSpeedPerVoltTimeConstantPeriods control periods, the motor's back-EMF, more than the mechanism's inertia, sets how fast it moves, so its position is first order with its speed per volt as b0. Otherwise it is second order with its acceleration per volt as b0. Both are in the loop's units. It needs the mechanism's moment of inertia.

ARM 

An arm's position loop; the same as POSITION.

PIVOT 

A pivot's or turret's position loop; the same as POSITION.

ELEVATOR 

An elevator's position loop, in a linear closed loop: POSITION in meters. Without a moment of inertia, it is first order with its speed per volt as b0, since an elevator's speed is nearly always set by its motor's back-EMF. The motor config must use a linear closed loop.

◆ WithBackEmfModel()

ADRCConfig & yams::math::ADRCConfig::WithBackEmfModel ( bool backEmfModel)

Choose whether the observer models the motor's back-EMF. On by default.

A motor's back-EMF brakes the mechanism in proportion to its speed. Left out of the observer's model, it is lumped into the disturbance the observer estimates, which then changes as fast as the speed does: the observer lags it whenever the mechanism speeds up or slows down, and a mechanism following a motion profile overshoots. Modeled, the disturbance only holds what the model misses, such as gravity and friction.

It applies to a position loop that chose second order when built from a motor config (see SystemOrder::POSITION), whose back-EMF time constant comes from the motor, the gearing and the moment of inertia. A first order position loop's b0, a speed per volt, already includes the back-EMF. A FLYWHEEL still lumps it into the disturbance. FIRST to FOURTH leave the model to you. To cancel the modeled back-EMF, the control law pushes with the observer's estimated speed, which cancels the damping the back-EMF gives the motor, so a loop whose timing is far from what it was built for can be better off without it. Changing it on a built config works the gains out again.

Parameters
backEmfModelWhether to model the back-EMF.
Returns
This config for chaining.
